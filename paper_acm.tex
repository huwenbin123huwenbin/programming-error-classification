% ABSTRACT
% ============================================================
\begin{abstract}

\par\textbf{Context}: Most automated verdict classifiers for programming submissions require source-code access or costly LLM inference, yet competitive-programming platforms already return rich execution metadata with every submission. How much verdict information that metadata carries, and where it stops carrying it, has not been established.

\par\textbf{Objectives}: This study asks how much verdict information is recoverable from metadata alone, and where that information stops---a boundary we term the \emph{platform-encoding boundary}---by comparing traditional machine learning (ML) with two large language models (LLMs) under a standardized protocol.

\par\textbf{Participants}: 13,360 incorrect submissions from 4,005 programmers on Codeforces (problem rating 800--3,500, median 1,300; median two submissions per programmer), covering five verdicts: Wrong Answer 76.6\%, Time Limit Exceeded 9.6\%, Compilation Error 7.3\%, Runtime Error 4.9\%, and Memory Limit Exceeded 1.5\%. These are competitive programmers, not a classroom population; we treat them as a large, publicly observable proxy and state the limits of that substitution explicitly.

\par\textbf{Study Methods}: Random Forest, Gradient Boosting, and Logistic Regression were trained on the six metadata fields the platform returns with every submission; DeepSeek-V3 (API) and \texttt{Qwen2.5:3B} (local) were prompted with three worked examples on five of those fields. Evaluation used a stratified 80/20 split (10,688/2,672), five-fold cross-validation, McNemar tests with Bonferroni correction, systematic ablation, a submitter-disjoint replication, and a direct analysis of observational equivalence in the metadata space.

\par\textbf{Findings}: The limit is set by observational equivalence rather than by model capacity. Of the 13,360 submissions, 1,504 (11.3\%) report 0\,ms, 0\,KB and 0 tests passed while spanning three verdicts---a compilation error, an early crash and a wrong answer on the first test all leave the same trace---so no metadata-only method can separate them, and Compilation Error is capped at F1 $\approx$ 0.77 by that class alone. Time Limit Exceeded (F1 0.99) and Memory Limit Exceeded (0.95) are fully recoverable because the platform's thresholds define them. Gradient Boosting reaches 91.77\% accuracy (balanced 0.80), Random Forest 91.80\%, and Logistic Regression 85.63\% but with Macro F1 0.49, since a linear boundary cannot represent a conjunction of zero-valued measurements. Runtime Error stays unreachable (F1 0.33; 94 of 131 errors reported as Wrong Answer), and more than half of those errors fall in signature cells shared with Wrong Answer. DeepSeek-V3 reaches 76.65\% on valid outputs, statistically indistinguishable from always answering Wrong Answer (76.61\%), while recovering every compilation error at 32\% precision; \texttt{Qwen2.5:3B} reaches 35.50\%. Supervised ML leads the strongest LLM by 15.1\,pp ($p < 0.001$), and a submitter-disjoint replication preserves both the ranking and the boundary (93.13\%).

\par\textbf{Implications}: Metadata-only screening can automate feedback for platform-measured verdicts at negligible cost, latency, and privacy exposure, but it cannot separate Wrong Answer from Runtime Error, the boundary where the two verdicts differ by an event the log never records. These results define what a submission log alone can and cannot tell a learner, and they motivate classroom validation before any claim about learning impact. Dataset and pipeline are released at \url{https://github.com/huwenbin123huwenbin/programming-error-classification}.
\end{abstract}

% 1. INTRODUCTION

\section{Introduction}

Introductory programming courses report non-completion rates of roughly a
third~\cite{bennedsen2007failure,watson2014failure}, with debugging difficulty as a primary obstacle~\cite{watson2014failure,spohrer1986novice}. Prior work analyzed compilation behavior~\cite{jadud2006methods} and scaled to
large populations via Blackbox~\cite{brown2014blackbox}, which made
IDE interaction logs from a worldwide novice population available for re-use. Competitive programming platforms such as Codeforces and LeetCode provide structured metadata (execution time, memory consumption, precise error verdicts, test cases passed) for every submission, making them valuable environments for studying programming error patterns at scale.

A central methodological consideration motivates this work. Competitive
programming platforms return structured verdicts for every submission, but the
specific metadata available and the granularity of verdict taxonomies vary across
platforms. For three of the five verdict types, the platform's execution
environment creates distinctive metadata signatures: a Compilation Error executes
in near-zero time (the compiler does not run), a Time Limit Exceeded submission
runs to the time limit, and a Memory Limit Exceeded submission exhausts the memory
limit. These three verdict types therefore produce predictable metadata patterns
that a classifier can learn: CE is associated with \texttt{time\_consumed $\approx$ 0},
TLE with \texttt{time\_consumed $\approx$ limit}, and MLE with \texttt{memory\_consumed $\approx$ limit}.
If these three verdicts are recoverable from metadata, the same decomposition
should hold on any platform whose judge measures wall-clock time and peak memory,
even though thresholds and verdict vocabularies differ across platforms.

The question then becomes: \emph{what verdict information is genuinely
recoverable from metadata beyond these platform-encoded cases?}
We define the \textbf{platform-encoding boundary} as the point at which verdict
information is reliably recoverable from submission metadata alone, without
requiring source-code access. The boundary is a property of how a platform
defines its verdicts, not of any particular classifier, which is why it should be
characterized rather than merely measured: a model that recovers CE from a
zero-millisecond execution time has not discovered anything about the submitted
program, but it has identified a verdict an institution can automate and,
therefore, the point at which automation must stop. The WA$\leftrightarrow$RE
boundary represents the residual uncertainty where neither error type produces
distinctive execution signatures, and where source-code analysis may become
necessary. Our study is organized around this decomposition.



Prior work has studied LLM-based programming feedback~\cite{raihan2025large,finnie2022robots}
and source-code analysis for programming error classification~\cite{feng2020codebert};
we review this literature in Section~2.

We investigate three research questions:

\begin{itemize}
 \item \textbf{RQ1:} What are the prevalent programming error patterns in competitive
 programming submissions, and how do they distribute across error categories?
 \item \textbf{RQ2:} How do traditional ML classifiers perform on metadata-based
 verdict classification, which features are most predictive, and how stable are predictions?
 \item \textbf{RQ3:} Where does the platform-encoding boundary lie---can ML or LLMs distinguish
 Wrong Answer from Runtime Error---and what are the accuracy--cost tradeoffs?
\end{itemize}

\paragraph{What this study does, and does not, claim.} The overall ranking we
report---supervised ML above prompted LLMs---is consistent with evidence that
LLM decisions on tabular inputs carry what the model inherited during
pretraining rather than only what the supplied field values say~\cite{liu2024confronting}, and
we therefore do not treat that ranking as our contribution. A ranking answers
which model wins on one dataset; it does not tell an instructor which feedback can
be automated and which cannot. What we contribute is the decomposition itself:
where the boundary falls, what sets it, how much of the headline accuracy it
accounts for (18.5\% of submissions), and what the residue implies for the
design of automated feedback.

Our contributions are:

\begin{enumerate}
 \item \textbf{An identifiability account of the boundary.} We show that the
 ceiling on metadata-based verdict classification is set by \emph{observational
 equivalence}---submissions whose metadata vectors coincide while their verdicts
 differ---rather than by model capacity. One signature (0\,ms, 0\,KB, 0 tests)
 covers 11.3\% of the corpus across three verdicts and bounds Compilation Error
 at F1 $\approx 0.77$; a second (31\,ms, 0\,KB, 1 test) covers a further 13.0\%
 and bounds the Wrong Answer$\leftrightarrow$Runtime Error distinction. Because
 the argument is model-free, it holds for any classifier given these inputs, and
 it explains why the residual errors are irreducible rather than merely unfixed.
 \item \textbf{Systematic comparative study} of ML and LLM methods for verdict
 classification from submission metadata, under a shared test split and a common
 feature vocabulary: three ML models and two LLM configurations, five-fold
 cross-validation, systematic ablation, corrected McNemar tests, and a
 submitter-disjoint replication.
 \item \textbf{Deployment guidance with a leakage-free protocol.} Execution time
 and memory dominate (a 7.3\,pp drop when time is removed, and 89.0\% of Gini
 importance between the two fields, 81.5\% of it from time alone), a
 submitter-history aggregate adds no gain that survives correction and is
 exactly zero when submitters are disjoint, and supervised ensembles lead the
 strongest prompted LLM by
 15.1\,pp at four to five orders of magnitude lower per-prediction inference
 cost (measured; Table~\ref{tab:llm-results}).
 Dataset and code: \url{https://github.com/huwenbin123huwenbin/programming-error-classification}.
\end{enumerate}

\paragraph{Student-population disclaimer.} Our dataset comes from competitive programmers (Codeforces rating 800--3,500), a population with substantially different error profiles from CS1/CS2 students. Prior work (Altadmri \& Brown, 2015) reports that 47.6\% of novice compilation events fail to compile (17.7M of 37.2M) against 7.3\% compilation-error verdicts in our dataset, and novices rarely produce TLE or MLE. The 91.8\% accuracy figure reflects competitive-programming error distributions; cross-platform and student-population validation are necessary before drawing conclusions about learning impact. We address this in Section~\ref{sec:skill-tier} (skill-tier analysis) and Section~\ref{sec:threats} (external validity). \textit{Feature-availability caveat:} the six fields we use are computable at first contact with a submission, so the pipeline carries no cold-start penalty; an earlier version of this work included a submitter-history aggregate, which we removed after its gain proved unreliable---nominal at best, and exactly zero once submitters are disjoint (Section~\ref{sec:ablation}).

\section{Related Work}

\subsection{Programming Error Analysis}

The study of programming errors has a history spanning over four decades
in computing education research~\cite{winslow1996programming}. This psychological perspective on
programming pedagogy highlights the cognitive demands debugging places on novices~\cite{winslow1996programming}.
McCauley et al.\cite{mccauley2008evidence} conducted a comprehensive review of the
novice debugging literature, organised around four questions: why bugs occur,
what types of bugs occur, how novices debug, and how instruction can help. They
found that the tools available to novices rarely support them in diagnosing and
fixing their own errors. This finding underscores the need for automated tools that can
accelerate the development of debugging proficiency. Cognitive Load Theory~\cite{sweller2011cognitive} posits that debugging simultaneously
taxes working memory across error diagnosis, code comprehension, and solution planning,
creating intrinsic overload that constrains novice self-correction~\cite{kirschner2018cognitive}. In this vein, Jadud~\cite{jadud2006methods} pioneered compilation event analysis using the BlueJ IDE, establishing compilation behavior as a data source for educational mining. The Blackbox project~\cite{brown2014blackbox} scaled this to a perpetual, worldwide collection from BlueJ users---over one hundred thousand opted in during its first year---and released the data for re-use by other researchers.

Large-scale analyses~\cite{ahadi2015exploring,luxton2018introductory} established that programming mistakes persist across cohorts and that the composition of those mistakes shifts over a course~\cite{altadmri2015most}, motivating automated diagnostic tools~\cite{barbosa2023feedback}.

Spohrer and Soloway~\cite{spohrer1986novice} showed, in a study of novice
Pascal programs, that the folk wisdom about novice mistakes cuts both ways: a
few bug types do account for most mistakes, but most bugs do not stem from
misconceptions about language constructs---they arise from difficulties
composing plans. Many errors that look
superficial have deeper cognitive roots, indicating that effective automated
feedback must identify the underlying error pattern rather than assume a small
catalogue of causes. Students' self-efficacy beliefs compound this challenge. Gorson and O'Rourke~\cite{gorson2020why} surveyed 214 CS1 students across three
universities and found that students reported negative self-assessments at each
of thirteen ordinary programming moments---including after a program ran
correctly---and that students who self-assessed negatively more often also
reported lower self-efficacy.

Busjahn et al.~\cite{busjahn2015eye} further revealed through eye-tracking studies that even expert programmers do not process code linearly, complicating error diagnosis and self-correction across all skill levels. 

\subsection{Machine Learning in Computing Education}

Machine learning has been increasingly applied to computing education
challenges over the past fifteen years. Educational data mining has identified programming education as a key application domain~\cite{romero2013data,baker2009educational}, with prediction tasks dominating the literature. Metadata-based approaches achieve strong performance~\cite{jadud2006methods,altadmri2015most}, while deep learning enables knowledge tracing in code-based learning~\cite{piech2015deep}.

Behavioral features from early assignments---compilation frequency, error diversity, time-on-task---can predict course outcomes~\cite{jadud2006methods,brown2014blackbox}, enabling early intervention through instructor-facing dashboards~\cite{jayaprakash2014early,verbert2013learning}.

Effenberger and Pel\'{a}nek~\cite{effenberger2021validity} show that the standard
way of validating student models---predicting the correctness of the next
answer---cannot distinguish models that use binary correctness from models that
use richer process data, so richer performance signals need their own validation
regime. Their point bears directly on our evaluation choices: an accuracy figure
alone cannot tell whether a model has learned the verdict or the class prior.

Verdict classification from submission data has been approached from two
directions that have not met on this task: compilation-behavior analysis,
which established that execution traces carry signal about novice
mistakes~\cite{jadud2006methods,altadmri2015most}, and semantic
representations of program structure. Neither asks what a submission log
alone says about the judge's verdict. Our approach asks exactly that with
metadata only---no source-code access, no code-feature extraction
pipeline---and reaches 91.8\% accuracy on a five-class verdict task, a
practical screening layer for platform-scale deployment. Allamanis et al.~\cite{allamanis2018learning} demonstrated that
graph-based representations of program structure capture semantically
meaningful features for code-related prediction tasks, motivating the
incorporation of such learned representations into verdict classification.

Alnahhas and Mourtada~\cite{alnahhas2020predicting} predicted the
performance of competitive programming contestants using account-level
metadata (rating, participation frequency, problem-difficulty distribution),
demonstrating that non-code features carry substantial signal for programming
behavior analysis. While their focus was on performance prediction rather than
verdict classification, their work demonstrates the continued relevance of simple,
interpretable models
in educational contexts.

Automated program repair (APR) methods~\cite{monperrus2018automatic} address similar diagnostic challenges at the source-code level, automatically localizing bugs and suggesting fixes. While effective, APR requires full code access and substantial computational resources, limiting deployment at platform scale. Our metadata-based approach complements APR by providing lightweight error-type inference without code access, serving as a screening layer to determine when deeper source-code analysis is warranted.

\subsection{Large Language Models in Programming}

Large language models have rapidly transformed expectations for automated code
understanding and generation~\cite{barke2023grounded,becker2023programming}. Barke et al.~\cite{barke2023grounded} demonstrated that programmer interaction with code-generating models differs fundamentally from traditional IDE usage. Finnie-Ansley et al.~\cite{finnie2022robots} found that OpenAI Codex placed in the
top quartile of CS1 students on examination questions---solving ten of 23 on the
first attempt and all but four within ten attempts---raising over-reliance concerns. Sarsa et al.\ showed that LLMs can generate usable programming exercises and
explanations, though only about 30\% of the generated sample solutions passed
the tests generated alongside them~\cite{sarsa2022automatic}, and Leinonen et al.~\cite{leinonen2023llm} found that LLM-generated
error-message explanations were rated an improvement over the original message
in only about half of cases (54\%), with the accompanying fix correct roughly a
third of the time---useful, but nowhere near reliable enough to hand to a novice
unattended.

Feng et al.~\cite{feng2020codebert} showed that CodeBERT achieves state-of-the-art performance on natural-language code search and code documentation generation, but is evaluated on source-code inputs; its effectiveness on submission metadata alone remains unclear. Evaluations of
LLM-generated feedback caution that such feedback can be flawed or
misleading---and therefore detrimental to learning---and that the automated
judges used to score it can be systematically over-optimistic~\cite{koutcheme2024opensource}---directly relevant to our finding that RE remains the most challenging category, where \texttt{Qwen2.5:3B} also struggled.

Recent work has examined how programmers and novices interact with LLM code
generators~\cite{barke2023grounded,becker2023programming,finnie2022robots}, and how
instructors are beginning to incorporate generative AI into their courses~\cite{prather2024instructors}. Keuning et al.\ survey automated feedback generation for
programming exercises and find that it rarely extends to formative, next-step
guidance~\cite{keuning2018systematic}. None of this work, however, compares
supervised classifiers against prompted LLMs on real submission metadata, which
is the boundary we characterise here.

\subsection{Metadata-Based Classification in Educational Contexts}

While source-code analysis (ASTs, token sequences, code embeddings) has
received considerable attention in computing education research, a parallel
line of work has demonstrated that \textit{submission metadata alone} can
achieve strong predictive performance for a range of educational outcomes.
Jadud~\cite{jadud2006methods} introduced the error quotient, a measure of how
efficiently a student clears syntax errors, and reported that it correlates
significantly with conventional indicators of academic progress. The Blackbox
project~\cite{brown2014blackbox} scaled the approach to a perpetual worldwide
collection from BlueJ users---over one hundred thousand opted in within its
first year---and released the data for re-use, establishing behavioural metadata
(compilation sequences, time-on-task, submission frequency) as a rich and
continuously available signal for educational data mining.

Prior work has shown that features derived from early
programming submissions---including compilation frequency, error diversity,
and time-on-task---can predict final course grades using only metadata,
without accessing student source code~\cite{jadud2006methods,brown2014blackbox}. Ahadi et
al.~\cite{ahadi2015exploring} extended this line with supervised learning on
naturally accumulating programming process data, separating high- and
low-performing students after the first week of an introductory course. Altadmri and Brown~\cite{altadmri2015most} analysed 37M Java
compilations from over 250{,}000 Blackbox users and grouped the
compiler-detected mistakes they found into three categories---syntax, type and
other semantic---with mismatched brackets the single most frequent. The dataset
records no runtime-error or wrong-answer verdicts at all, because those failures
produce no compiler diagnostic, so it yields no submission-level verdict
distribution for a novice population. This is a different measurement problem
from ours rather than a comparable baseline, and it motivates cross-population
validation of automated classification tools: Petersen et
al.~\cite{petersen2015exploration} showed that even an established behavioral
metric such as the Error Quotient shifts meaningfully across course contexts, and
argued that such metrics are typically developed and validated in narrow
settings. Related work further established that
\textit{behavioral signals} from the first four weeks of a semester---compilation frequency, error diversity, and time-on-task---are sufficient to identify students at risk of failure, enabling early
intervention without privacy-invasive code monitoring~\cite{jadud2006methods,brown2014blackbox}.

In the context of competitive programming platforms, Alnahhas and
Mourtada~\cite{alnahhas2020predicting} used account-level metadata (historical
rating sequences) to predict contestants' future ratings, finding that a deep
model beat five classical baselines. Their task is regression on a rating
trajectory rather than classification of a submission, but it establishes the
premise we build on: account-level metadata alone carries substantial signal
about programming behaviour.

The advantages of metadata-based classification are both practical and
privacy-preserving: (1) no source code access is required, avoiding
potential concerns about student code being processed by third-party APIs;
(2) computational cost is orders of magnitude lower than code-based
approaches (no tokenization, AST parsing, or GPU inference); and
(3) deployment at platform scale (millions of daily submissions) becomes
feasible with modest computational resources. A central open question
is whether metadata alone can achieve competitive accuracy against
code-based approaches---a question this study addresses
systematically for the verdict classification task.

 

\par\textbf{Contribution boundary}: Prior work on metadata-based prediction has focused primarily on \textit{grade prediction} and \textit{at-risk identification}; we are not aware of any study that applies metadata-based classification to the more granular task of \textit{verdict classification}, or that compares metadata-based ML with LLM prompting on the same task and data. Three specific gaps follow:

\begin{enumerate}
 \item \textbf{Metadata-based classification}: Existing verdict classification
 studies focus on source code analysis, neglecting the rich diagnostic
 signals in submission metadata (execution time, memory usage, test cases
 passed).
 \item \textbf{ML--LLM comparison}: No work systematically compares traditional
 ML (RF, GB, LR) and two LLM configurations (DeepSeek-V3, \texttt{Qwen2.5:3B})
 on identical verdict classification tasks.
 \item \textbf{Feature importance quantification}: While execution time has been
 hypothesized as important, no study quantifies feature importance through
 systematic ablation with statistical significance testing.
\end{enumerate}

Our work addresses all three gaps by providing a systematic comparison
of ML and LLM methods for metadata-based verdict classification, with
feature ablation and McNemar significance testing.

\section{Methodology}

\subsection{Dataset Collection}

We collected submission data from Codeforces, a competitive programming platform widely used for algorithmic training and education~\cite{mirzayanov2020codeforces,zhang2022automated} (\url{https://codeforces.com/})
via the official public REST API. The Codeforces
platform was selected for three reasons: (1) it provides structured, rich
metadata for every submission including precise execution time, memory usage,
and error verdict; (2) it represents an ecologically valid competitive
programming environment with high participant engagement; and (3) it has a
large, diverse problem set covering a wide range of algorithmic domains and
difficulty levels.

These properties make Codeforces uniquely suited to the present research
questions. Its per-submission execution telemetry (time, memory, verdict) is
exactly the metadata required to test the platform-encoding boundary, and its
scale supports both class-balanced evaluation across five verdict types and
user-level clustering analysis (Section~\ref{sec:threats}). We acknowledge that
competitive programmers differ from CS1/CS2 students (Section~\ref{sec:threats});
cross-population validation on CS1QA and Blackbox remains future work
(Section~\ref{sec:future}).

Submissions were retrieved from competitive programmers with Codeforces
ratings spanning 800 to 3500 (corresponding to Newbie through Legendary
Grandmaster levels). This range was deliberately chosen to represent
proficient programmers who produce a variety of error types and for whom
submission metadata is meaningfully differentiated. Data collection was
completed in June 2026, covering submissions from November 2020 to June
2026, providing approximately 5.5 years of programming activity. The final
dataset contains 13,360 submissions from 4,005 distinct programmers; the median
programmer contributes two submissions and 773 programmers contribute five or
more, so the sample is broad rather than deep, a property we return to in
Section~\ref{sec:limitations}.

\paragraph{Ethics review.} The data are public submissions retrieved through the
Codeforces public REST API under the platform's terms of service. There was no
interaction with human participants, no access to private student records or
institutional course data, and no collection of demographic attributes;
programmer handles were replaced with anonymized identifiers before analysis. No
informed consent was obtained, because the submissions were already public and
the analysis is secondary. Under the policy of the Xijing University
Institutional Review Board, secondary analysis of publicly available data does
not constitute human-subjects research, and the study was determined to be
exempt from IRB review (Section~\ref{sec:ethics}).

\subsubsection*{Collection Pipeline}
The data collection and preparation proceeded as follows (details in
Data Cleaning below):
\begin{enumerate}
 \item Raw collection: error submissions retrieved from the
 Codeforces public REST API (Nov 2020--Jun 2026).
 \item Filtering: submissions with missing execution time, memory, or
 verdict fields were removed.
 \item Deduplication: duplicate entries were removed and only the final
 submission per (user, problem) pair was retained to prevent
 train--test leakage.
 \item Final dataset: \textbf{13,360} error samples from competitive
 programmers across hundreds of Codeforces contests
\end{enumerate}

\subsubsection*{Data Cleaning}
Data cleaning was performed in three stages. First, submissions with
incomplete metadata (missing execution time, memory, or verdict fields) were
removed. Second, duplicate entries (identical submission timestamps and
verdicts) were deduplicated. Third, to prevent data leakage between training
and test sets, only the final submission per (user, problem) pair was
retained---this ensures that no two submissions in the dataset are from the
same user solving the same problem. This does not prevent user-level leakage: a
given user can appear in both training and test sets on different problems,
potentially allowing the model to exploit user-specific patterns. A
submitter-level aggregate computed over the whole corpus would let each row's
own label enter its own predictor; built from earlier training submissions
only, such a field adds no gain that survives correction
(Section~\ref{sec:ablation}), so we excluded submitter-level aggregates from
the model after testing them. Stratified sampling ensures that no single
submitter dominates any fold (the largest submitter occupies 1.1\% of the test
fold). To confirm that the
reported accuracy does not depend on seeing the same person on both sides of the
partition, we additionally ran a fully submitter-disjoint replication, with zero
overlap and no aggregate features available for unseen submitters; Gradient
Boosting retained 93.13\% (Section~\ref{sec:robust}).

The final dataset comprises 13,360 error submissions from competitive programmers
across hundreds of Codeforces contests. Table~\ref{tab:error-dist} summarizes
the error type distribution. The language distribution
is predominantly C++ (C++23 41.1\%, C++17 24.1\%, C++20 19.6\%; 85.2\% of
submissions in total), with Python and PyPy (6.2\%), Java (3.3\%), and other
languages representing smaller fractions. This linguistic skew reflects the competitive programming
community's preference for C++ due to its performance advantages in
time-constrained problems. Pairwise feature correlations are weak to moderate (Figure~\ref{fig:corr}).

\subsection{Feature Engineering}\label{sec:features}

Six fields are extracted from each submission. All six appear in the public
submission record that the Codeforces API returns, so the pipeline needs
neither source code nor an authenticated session:

\begin{enumerate}
 \item \textbf{problem\_rating}: integer difficulty rating (800--3500),
 indicating the algorithmic complexity of the problem.
 \item \textbf{language\_encoded}: programming language (35 distinct compiler
 and interpreter identities in the corpus, dominated by C++17/20/23),
 capturing language-specific failure modes.
 \item \textbf{time\_consumed\_ms}: wall-clock execution time of the slowest
 test that ran, in milliseconds.
 \item \textbf{memory\_kb}: peak memory reported by the judge, in kilobytes.
 \item \textbf{problem\_slot}: the lettered position of the problem within its
 contest (A, B, C, \ldots), an ordinal proxy for expected difficulty within a
 round; it correlates with \texttt{problem\_rating} at $r=0.74$.
 \item \textbf{passed\_test\_count}: the number of judge tests the submission
 passed before the run was stopped.
\end{enumerate}

Two further candidates appear routinely in the learning-analytics literature.
We tried both and report why neither is used, because each failure is
instructive.

\emph{Submission time.} An hour-of-day feature is often read as a proxy for
time-on-task or late-night work. The public submission record carries no
timestamp---only a contest identifier---so the field cannot be constructed from
the released data. An earlier version of this pipeline set it to a constant,
which is indistinguishable from omitting it; we omit it.

\emph{Submitter history.} A user-level aggregate (historical WA rate, or its
complement, a success rate) summarises proficiency and is the single most common
feature in grade-prediction work. No success rate can be formed from this
corpus, which contains only failing submissions. A WA-rate aggregate can, and
Section~\ref{sec:ablation} tests it: computed over the whole corpus it appears
to add 3.7 percentage points, but that is each row's own label entering its own
predictor; computed from the submitter's earlier training submissions only it
adds 0.67\,pp, which does not survive correction for the seven comparisons and
is exactly zero on the submitter-disjoint split. The field is excluded rather
than repaired.

The restriction has a practical justification as well. A deployed classifier
sees a submission from a student it has never met, so a field requiring prior
history is unavailable exactly when feedback is most valuable. The six retained
fields are computable at first contact with a submission.

These fields were selected because they are available without source-code
access, they span the problem, the program and the judge's measurement of it,
and each has prior support in educational data mining.

\subsubsection*{Theoretical Framework: Feedback and Self-Efficacy}

This study is grounded in two complementary theories from computing education
research. First, Hattie and Timperley's model of effective
feedback~\cite{hattie2007power} identifies four levels: task, process,
self-regulation, and self. Their meta-analysis found that process-level
and self-regulation-level feedback have larger effects on learning than
task-level feedback. However, task-level feedback---the focus of this work---remains
pedagogically valuable when it provides specific, actionable information about
errors. Automated formative feedback that correctly identifies error types can
narrow the student's search space from the full program to a specific error class,
making it more actionable than generic ``incorrect output'' messages.

Second, Bandura's self-efficacy theory~\cite{bandura1997self} posits that
accurate performance feedback is a primary driver of self-efficacy beliefs.
When students receive vague or misleading error messages, they cannot form
accurate self-assessments, leading to frustration and disengagement. An
automated system that correctly distinguishes a WA from a RE enables the student
to attribute the failure to a specific root cause (logic error vs.\ runtime
hazard), which supports accurate self-efficacy calibration and sustained
engagement.

The present study operationalizes these theories by asking: \textit{How much
error-type information is recoverable from submission metadata alone, without
source-code access?} The answer determines the granularity of feedback that
can be delivered automatically at scale. Our findings inform one boundary condition:
when WA$\leftrightarrow$RE cannot be distinguished from metadata alone, the finest-grained
task-level feedback (distinguishing logic errors from runtime failures) may require
source-code analysis. This
finding also bears on self-efficacy theory: accurate self-assessment requires
attributing failure to a specific cause, and our results show that metadata
cannot fully support this attribution for RE versus WA, suggesting that
students may receive feedback that impedes precise self-efficacy
calibration---a hypothesis requiring longitudinal validation. These theoretical
predictions are \emph{consistent with} our empirical findings; causal validation
would require a controlled study measuring student self-efficacy and learning
outcomes, which is beyond the scope of this work.

\subsubsection*{Feature Selection Rationale}

The six fields satisfy three criteria: they are available from the platform API
without source-code access; each captures a distinct aspect of the submission
(difficulty, implementation, execution); and together they cover the
problem-level, program-level and judge-level views that the boundary argument
requires. No a-priori selection was applied, so that the ablation study in
Section~\ref{sec:ablation} can speak to each field's contribution.

Tree ensembles were fitted on raw values, since axis-aligned splits are
invariant to monotone rescaling; the linear baseline was standardized. The
largest pairwise correlation is between \texttt{problem\_rating} and
\texttt{problem\_slot} ($\rho=0.74$), which is expected---later slots hold
harder problems---and is harmless for tree models, where a correlated pair
simply shares credit. Time and memory correlate at $\rho=0.33$, and the
remaining pairs fall below $0.40$.

\textbf{\texttt{passed\_test\_count} and verdict collinearity.} This field is
partly collinear with the verdict, by construction: every compilation error has
a count of zero, because nothing was executed. Point-biserial correlations with
the indicator of each class are $r=-0.107$ for CE ($p<10^{-35}$), $r=0.322$ for
TLE ($p<10^{-300}$) and $r=0.206$ for MLE ($p<10^{-120}$); for WA the relation
is weaker ($r=-0.233$), with 69.7\% of wrong answers having passed at least one
test (mean 1.31). The field therefore does not encode WA deterministically. Its
marginal contribution is small but non-zero: removing it from the six-field
model costs 0.22 percentage points (Table~\ref{tab:ablation}), compared with
7.30 for execution time. Its value is architectural rather than predictive---it
is the field that makes the all-zero equivalence class of Section~5.3 legible,
since a count of zero is what a failed compilation, an early crash and a
first-test wrong answer have in common.

\subsection{Experimental Models}\label{sec:models}

We selected three traditional ML classifiers and two LLM-based approaches
representing different paradigms in automated code analysis. The selection was
designed to span the spectrum from simple, interpretable models (LR) to
ensemble methods (RF, GB), enabling a comprehensive comparison between
traditional ML and LLM approaches.

\subsubsection*{Traditional ML Classifiers}
\begin{itemize}
 \item \textbf{Random Forest (RF)}: An ensemble of 100 decision trees using
 Gini impurity for splitting~\cite{breiman2001random}, with unlimited
 max depth, minimum samples split of 2, and minimum samples leaf of 1.
 Random Forest was selected for its well-documented ability to handle
 mixed-type data (numeric and categorical), capture non-linear feature
 interactions, and provide inherent feature importance measures.
 \item \textbf{Gradient Boosting (GB)}: An ensemble of 100 staged
 decision trees using gradient descent
 optimization~\cite{friedman2001greedy}, with max depth
 of 3 (shallow trees to prevent overfitting), learning rate of 0.1,
 and subsample of 1.0. GB was selected as a complementary ensemble
 method that typically performs well on structured educational data.
 \item \textbf{Logistic Regression (LR)}: Multinomial logistic regression
 with L2 regularization~\cite{hosmer2013logistic}, L-BFGS solver, fitted on
 standardized features (the raw fields span five orders of magnitude, and an
 unstandardized fit does not converge). LR is included as an interpretable
 floor, not as a competitor; Section~4.2 shows why a linear boundary cannot
 represent the conjunction that defines a compilation error.
\end{itemize}

All traditional ML models were implemented using scikit-learn
1.6.1~\cite{pedregosa2011scikit} with default parameters unless otherwise
specified. Hyperparameter tuning was initially explored using grid search
with 3-fold cross-validation on a 10\% held-out validation set, but the
performance gains were marginal ($< 1\%$ for tuned vs.\ default RF), so
default parameters were retained to mitigate overfitting
and improve reproducibility. The random state was set to 42 for
reproducibility. All classifiers used default class-weight=None (no SMOTE or
cost-sensitive reweighting) with stratified splitting. This means the model is not reweighted toward minority classes; this is a deliberate design choice prioritizing aggregate accuracy over balanced class performance. Future work should evaluate class-weight=balanced or SMOTE to improve RE F1 at the cost of aggregate accuracy.

\subsubsection*{LLM-Based Approaches}
Two LLM configurations were evaluated under an identical three-shot protocol,
both receiving the same five metadata fields (problem\_rating, language,
time\_consumed\_ms, memory\_kb, passed\_test\_count). Each request classified
eight submissions at a time and carried three worked examples (one each for CE,
TLE and MLE); language was shown as a normalized family (e.g.,
``C++23 (GCC 14-64, msys2)'' $\rightarrow$ ``C++''). Both models returned a
JSON object holding one verdict acronym (WA/TLE/RE/CE/MLE) per item:
\begin{itemize}
 \item \textbf{DeepSeek-V3~\cite{deepseek2024deepseekv3} (online, evaluated)}: A frontier online model
 accessed via the DeepSeek API, representing a strong,
 general-purpose LLM available without local compute.
 \item \textbf{\texttt{Qwen2.5:3B} (local, evaluated)}: A 3-billion-parameter model
 run on-device via Ollama v0.30.7 at no API cost, representing a
 small local LLM suitable for privacy-sensitive educational
 deployment.
\end{itemize}
Inference used temperature$=0$ and grammar-constrained JSON output to ensure
parsable responses; both models were evaluated on the same 2,672-sample test
set as the ML models. The exact prompt is reproduced in
Section~\ref{sec:prompt-template}.

\subsection{Evaluation Protocol}\label{sec:eval}

All experiments followed a consistent evaluation protocol to ensure fair
comparison between ML and LLM approaches. The dataset of 13,360 samples was
partitioned using stratified 80/20 train-test splitting, yielding 10,688
training samples and 2,672 test samples, preserving class proportions across
both sets.

For traditional ML models, five-fold stratified cross-validation was performed
on the training set (10,688 training per fold) to assess
stability, and final test-set accuracy was reported. For LLM-based methods, the test set of 2,672 samples was classified directly
using three-shot prompting: no fine-tuning, but three worked examples (one each for CE, TLE and MLE) prepended to every request, with eight submissions classified per call.
Unlike ML models, LLMs do not have a training phase in our protocol; we therefore
do not apply cross-validation to LLM results. A single fixed test-set evaluation
is reported for each LLM configuration, consistent with standard LLM benchmarking
Multiple random-seed repetitions would provide variance estimates; DeepSeek-V3 was evaluated with temperature$=0$ (deterministic API), so within-run variance is negligible and cross-run variance reflects only model-level non-determinism, which is minimal under this configuration. Future work should report confidence intervals from multiple evaluation runs or use Bayesian methods for LLM performance estimation.
Both DeepSeek-V3 (API) and \texttt{Qwen2.5:3B} (local Ollama) were evaluated under the
identical protocol.

Statistical significance of pairwise model comparisons was assessed using
McNemar's test~\cite{mcnemar1947note} ($\alpha = 0.05$), a non-parametric test
for paired nominal data appropriate for comparing classifiers on the same test
set. Feature ablation was conducted by removing each field in turn,
retraining GB on the remaining five, and measuring the accuracy drop on the same
test partition. Six ablations were run; the Bonferroni threshold for this family
is $\alpha' = 0.05/6 \approx 0.008$, and we report uncorrected $p$-values while
noting which survive it. Ablation is exploratory; the primary
multiple-comparison correction is applied to the ten pairwise model comparisons
in Table~\ref{tab:mcnemar} (Bonferroni $\alpha' = 0.005$).

Classification performance is reported as overall accuracy, per-class
precision, recall, and F1-score. Confusion matrices are provided for one of the
two tree ensembles (Gradient Boosting) to reveal class-wise error patterns. The
two are statistically indistinguishable on accuracy ($\chi^2=0.00$, $p=1.00$;
Random Forest scores 91.80\%, a difference of 0.04\,pp), and Gradient Boosting
is reported throughout because it carries the marginally higher macro F1
(0.799 against 0.798) and the tighter cross-validation spread; the matrices
below are therefore reported for Gradient Boosting, and all per-class
precision, recall and F1 values in the tables refer to that model. Confidence
intervals (95\%) for LLM performance are computed using the Wilson score
interval for binomial proportions.

\subsection{Where the Metadata Runs Out: Observational Equivalence}

Accuracy alone cannot say whether the residual errors are a modelling deficit
or a property of the data. We therefore characterise the metadata space
directly. Two submissions are \emph{observationally equivalent} when their
metadata vectors coincide but their verdicts differ. No function of the encoded
fields can separate such submissions: every classifier must choose a single
verdict (or a single posterior) for the whole cell, so precision and recall
trade off inside it and cannot both be maximised.

The equivalence classes are not a theoretical curiosity here. Of the 13,360
submissions, 1{,}504 (11.3\%) report exactly $0$\,ms, $0$\,KB and $0$ tests
passed. That single signature contains 980 compilation errors, 498 wrong
answers and 26 runtime errors. The reason is mechanical: when a submission
fails to compile, the judge has nothing to execute, so it reports zeros---but a
submission that fails on the very first test case, or that crashes before
producing output, produces the same zeros. The platform's report is identical
in all three situations.

This bound is visible in the fitted model. In the test partition, 315
submissions carry the all-zero signature: 196 compilation errors, 111 wrong
answers and 8 runtime errors. A rule that assigns the whole cell to CE attains
precision $196/315=0.62$ and recall $1.00$, i.e.\ F1 $=0.767$. Gradient
Boosting attains F1 $=0.770$ on CE, with recall $0.898$ and precision $0.674$.
The model has reached the ceiling that the signature imposes: every one of its
261 CE predictions lies inside the all-zero cell, and the 85 that are not
compilation errors are precisely the wrong answers and runtime errors carrying
that signature. The 23-point F1 shortfall is therefore not a
modelling failure but the price of a verdict the platform never recorded.

The second cell plays the same role for the other boundary. Of the 94 runtime
errors that Gradient Boosting assigns to WA, 53 fall in signature cells that
also contain WA submissions in the same partition, 45 of them in cells holding
at least five. For these submissions the WA and RE reports differ while every
recorded number agrees.

Table~\ref{tab:equivalence} lists the two largest mixed groups, which invites the
question of what the other 93 account for. The count is larger than the table
suggests: 95 signature groups contain more than one verdict and together cover
8{,}653 submissions (64.8\%). The mass, however, is concentrated in groups that
are mixed only nominally. Twenty-five of them hold 6{,}761 submissions (50.6\% of
the corpus) whose modal verdict accounts for 90--99\% of the group, so assigning
the whole group to that verdict costs a small fraction of its rows. All but one
of these 25 groups is Wrong-Answer dominated, so their near-purity reflects the
class prior rather than platform encoding and does not enlarge the set of
verdicts that can be automated. The remaining
70 groups hold 1{,}892 submissions (14.2\%), and these are the ones in which the
verdict genuinely cannot be recovered. A rule that reads nothing but (time,
memory, tests passed) and assigns each signature its majority verdict recovers
CE, TLE and MLE at recall 1.00, WA at 0.95 and RE at 0.44, for 6.6\% total error.
That rule is fitted on all labels, so it is a diagnostic ceiling rather than a
deployable classifier; its point is that the three execution-defined verdicts
need no learning at all once the judge's thresholds are read off, whereas RE is
the one verdict the signature genuinely loses. The boundary is therefore local
and locatable, not a diffuse failure spread across the feature space.

Execution time dominates: removing it costs 7.3 percentage points, more than
four times the next largest effect, and the model then misclassifies TLE
submissions that no longer look near the limit. Memory contributes 1.8\,pp,

are individually expendable---their removal costs between 0.07 and 0.64\,pp and
only language survives correction at $\alpha'=0.008$ (it does not; $p=0.031$).

The last row of Table~\ref{tab:ablation} addresses a question the earlier
literature leaves open. Aggregate features describing a submitter's history
are attractive in learning analytics, and a WA-rate aggregate computed over
the whole corpus appears to add 3.7 percentage points---95.43\% against the
91.77\% baseline. That number is an artefact of look-ahead: through the
aggregate, each row's own verdict feeds its own predictor. Computed without
look-ahead---each row seeing only its submitter's submissions that precede it
in submission order and fall in the training partition---the same field adds
0.67\,pp (92.44\%, $p=0.039$), a nominal gain that does not survive
correction for the seven comparisons ($\alpha'\approx0.007$). The estimate is
thin where it exists at all: among test rows whose submitter appears in
training it rests on a median of three earlier submissions, and 957 of the
2,672 test rows---new submitters, and submitters whose only earlier
submissions lie on the test side---collapse to the training prior. We exclude
the field for the reason that decides it: on the submitter-disjoint split
every one of the 2,460 test submitters is new, the aggregate is constant on
the test side, and accuracy holds at 93.13\% (34 of 2,460 predictions flip,
in balance). A field that pays only where history exists cannot serve the
cold-start population the platform actually presents; Section~\ref{sec:robust}
shows the exclusion costs nothing there.

Learning curves confirm that the gap to the LLMs is not a data-volume artefact.
Accuracy rises from 85.8\% at 200 training submissions to 87.7\% at 400 and
91.1\% at 2{,}800, reaching 91.8\% on the full 10{,}688-submission training
partition (mean of five repeats per size;
\texttt{experiment\_code/learning\_curve.py}). Already at 400
submissions---3.7\% of the available data---the model leads the strongest
prompted LLM by 11.1\,pp, so the 15.1\,pp gap at full data reflects the
feature class rather than the sample size; the remaining 0.7\,pp accrues over
the final three quarters of the training set.

excludes the cost of labelling 10,688 training submissions, which is the real
price of the supervised advantage.

\subsection{Robustness}
\label{sec:robust}

\paragraph{Submitter-disjoint replication.} Submissions are not independent
observations. The 4{,}005 submitters contribute a median of two submissions
each (maximum 134), and their verdict mixes are strongly concentrated: the mean
per-submitter modal-verdict share is 0.92 against a random baseline of 0.20,
and the ratio of per-submitter to global verdict-distribution entropy is 0.18.
A random split therefore places submissions from the same person on both sides
of the partition, and the McNemar $p$-values in Table~\ref{tab:mcnemar} should
be read as lower bounds on uncertainty.

To test whether the conclusions depend on this, we reran the full pipeline on a
submitter-disjoint partition (GroupShuffleSplit over \texttt{user\_handle},
zero overlap, $n_{\text{train}}=10{,}900$, $n_{\text{test}}=2{,}460$).
Gradient Boosting scores 93.13\% (CV 92.15\%), Random Forest 91.99\% and
Logistic Regression 87.15\%: no degradation relative to the random split, and
no rank change. The per-class structure is preserved---CE 0.788, TLE 1.000,
MLE 0.988, WA 0.957---with RE falling further to 0.256, as expected when the
boundary is exercised by unfamiliar submitters. Because the final model carries
no submitter-level aggregate, the cold-start setting requires no re-engineering.

\paragraph{Clustering-aware reading.} A cluster-robust correction (grouping
standard errors by submitter) would widen the intervals reported here and is
the appropriate choice for a confirmatory replication. The dependence is
substantial rather than marginal: the one-way intraclass correlation of the
verdict is 0.48 (per-class 0.40--0.53), so two submissions from the same
programmer agree on the verdict about half the time beyond chance. With a mean
of 3.34 submissions per submitter this implies a design effect of 2.13, i.e.\
the 13{,}360 submissions carry the information of roughly 6{,}300 independent
ones. We report unadjusted McNemar statistics with the clustering diagnostic
above so that the direction and rough magnitude of the dependence are visible.

\paragraph{Class imbalance.} Balanced accuracy is GB 0.804, RF 0.791, LR 0.486, DeepSeek-V3 0.708 and
\texttt{Qwen2.5:3B} 0.348. The ordering is preserved, so the ensemble advantage
is not an artefact of the WA majority. The gap between DeepSeek-V3's balanced
accuracy and its accuracy is itself informative: the model is a genuinely
different classifier from the majority rule, one that trades WA recall for the
execution-encoded classes.

\section{Discussion}

\subsection{Finding 1: The Boundary Is Set by Observational Equivalence}\label{sec:platform-encoding}

\paragraph{Answering the circularity objection.} A reader may object that
recovering CE, TLE and MLE from execution metadata is circular: the platform
defined these verdicts through the very measurements we feed the model, so the
classifier is re-reading a threshold. We accept the premise and draw a
different conclusion from it. Circularity would matter if the claim were that a
model had discovered something about the submitted program. Our claim is
narrower, and for an institution it is more useful: it identifies which verdicts
the platform has already decided, and therefore which feedback can be
reproduced from the submission log alone, without touching student code, at
microsecond cost and with no privacy exposure.

The same reasoning shows where the encoding stops. Because a verdict is recorded
through a finite set of measurements, two verdicts that produce identical
measurements become indistinguishable---not approximately, but exactly. That is
observational equivalence, and it converts a vague complaint (``metadata is
limited'') into a quantity: 11.3\% of this corpus lies in a single cell
spanning three verdicts, and 13.0\% in a second cell spanning two.

\paragraph{The encoding is faithful but not injective.} Compilation Error is the
clearest case, and also the most instructive failure. A submission that does not
compile executes nothing, so the judge reports 0\,ms, 0\,KB and 0 tests passed;
CE is therefore recoverable in principle from a single rule. Yet its F1 is 0.77,
not 0.99, because 498 wrong answers and 26 runtime errors in this corpus report
exactly the same three zeros: a program that crashes on the first test, or
answers the first test incorrectly, never gets far enough for the judge to
record anything else. Every one of the model's 261 CE predictions in the test
partition lies inside that cell, and the 85 that are wrong are the cell's
non-CE members. The model has extracted all the information the encoding
carries; the encoding itself is lossy.

This reframes the practical question. It is not ``which classifier handles CE
best''---every classifier is bounded by the same cell---but ``what else would
have to be recorded for the cell to split''. The answer is the compiler
diagnostic for CE and the failing test index for WA, neither of which is in the
public submission record but both of which the platform holds.

\paragraph{The second boundary.} Wrong Answer and Runtime Error differ by an
event the judge observes but does not publish: whether the process terminated
normally after printing the wrong answer, or died (segmentation fault, division
by zero, assertion) before finishing. The log records only the residue---time,
memory, tests passed---and that residue is shared: 1,682 wrong answers and 56
runtime errors occupy the same (31\,ms, 0\,KB, 1 test) cell. Consequently RE F1
is 0.33 with recall 0.22, and 53 of the 94 RE$\rightarrow$WA errors fall in
cells that also contain wrong answers in the same partition. This is where
source-code analysis would earn its cost, because the two root causes demand
different pedagogical responses---revise the algorithm versus fix an
out-of-bounds index---and the metadata cannot tell them apart.

\subsection{Finding 2: Execution Dominates, and History Does Not Help}

Execution time is the dominant predictor: removing it costs 7.3 percentage
points, four times the effect of the next field, and it carries 81.5\% of the
Gini importance. Peak memory contributes 1.8 percentage points and 7.5\% of
importance. Together the two fields the judge writes while running the program
account for 89.0\% of the model's decisions and for 11.1\% of the corpus being
recoverable at all. This is the platform-encoding account stated numerically:
what the model knows about a submission is almost entirely what the judge
measured about it.

The four problem-level fields contribute the rest and are individually
dispensable (0.07 to 0.64 percentage points). The most instructive negative
result concerns a field we removed. A submitter-history aggregate is the
standard first feature in grade prediction, and in our first pass it appeared
to add 3.7 percentage points. Computed without look-ahead---each row seeing
only its submitter's submissions that precede it in submission order and fall
in the training partition---the gain shrinks to 0.67\,pp and does not survive
correction for the seven comparisons; on the submitter-disjoint split it is
exactly zero, because every test submitter there is new. What looked like
signal in the first pass was the row's own label leaking into its own
predictor through the aggregate, a failure mode that is easy to miss and, in a
field where such aggregates are routine, worth flagging explicitly. It also
happens to be the field that would be unavailable for a new student, so
removing it costs nothing and simplifies the deployment story.

\subsection{Finding 3: Why Runtime Error Is Different}

The class imbalance (WA 76.6\% against MLE 1.5\%) explains why accuracy is a
poor summary of this task and why we report per-class F1 throughout. It does not
explain the RE failure, which is not a scarcity effect: RE is the fourth largest
class in the corpus (4.9\%), and the model sees 131 instances in the test
partition alone. The failure is structural. RE is not a behaviour the platform
measures; it is a behaviour the platform infers from the absence of a normal
exit, and the inference is under-determined by the fields it publishes.

This matters for how the result should be read. A model that reported RE with
high confidence would be over-claiming: precision on RE is 0.66, so when it
does commit it is usually right, but it labels only 44 of the 2,672 test
submissions as RE and catches 29 of the 131.
For a tutoring system the useful output here is not a forced label but the
abstention itself---flagging the submission as ``failed at runtime or produced a
wrong answer early'' and routing it to a diagnostic that reads the code.

\paragraph{Ranking and thresholding come apart.} Runtime Error is the clearest
case in which the model knows more than its label suggests. Its one-vs-rest
ROC AUC is 0.831, against an F1 of 0.33 at the argmax (Figure~\ref{fig:roc});
the macro one-vs-rest AUC is 0.955. The classifier orders runtime errors well
above wrong answers---it has extracted real signal from the shared execution
signature---but the two classes crowd together near the decision surface, so the
single cut that argmax imposes cannot deliver both precision and coverage. This
is what an equivalence class looks like from the model's side: the posterior is
informative, the label is not.

The practical consequence is that abstention can be examined rather than merely
recommended. Moving off the argmax to an explicit precision floor of 0.60 flags
38 submissions at precision 0.71 and recovers 21\% of runtime errors, against
44 flagged at precision 0.66 and 22\% recall under the argmax; a floor of 0.50
flags the same 44 submissions. The trades are marginal---raising the floor buys
a little precision with coverage it does not repay---and we report them as an
operating characteristic rather than a solution: they show that the RE posterior
carries usable ordering information even though the RE verdict does not survive
thresholding. Precision--recall curves for all five classes are released with
the reproduction script.

\subsection{LLM Error Analysis}\label{sec:llm-analysis}

The per-class behaviour of the two LLMs explains why their accuracy figures are
a poor guide to what they have learned (Table~\ref{tab:llm-analysis}).

DeepSeek-V3 is best understood as a threshold rule with no prior. It identifies
every compilation error in the test partition---recall 1.00---by firing on
submissions with very short execution times, and it recovers most TLE and MLE
submissions (0.87 and 0.88). Because it applies the rule unconditionally,
precision on CE falls to 0.321: 415 submissions whose true verdict is otherwise
(385 wrong answers, 27 runtime errors and 3 TLEs) with short execution times---
137 reporting exactly 0\,ms, the signature shown in the worked example, and the
remaining 278 spanning 1--1000\,ms (238 at $\le$31\,ms, the modal wrong-answer
times)---are reported as compilation errors. Its aggregate accuracy, 76.65\%, is
indistinguishable from always answering Wrong Answer (76.61\%), yet its balanced
accuracy is 0.708, close to the supervised model's 0.804. The LLM applies the
same platform encoding the tree ensemble found---it was shown one instance of
the zero-time$\rightarrow$CE mapping as a worked example and extended it to
every short-time submission---; what it lacks is the calibrated trade-off inside
the equivalence cell---the ability to say ``this cell is two thirds compilation
errors, so I will report CE and accept the loss''. Prompted with three worked
examples and no prior over the cell, it can only apply the rule or not apply
it.

The supervised model makes the opposite trade. It reports CE with precision
0.67 and recall 0.90, giving up 20 compilation errors to avoid 85 false ones,
and spends the recovered capacity on WA. That difference, rather than any
general superiority of gradient boosting over language models, is what the
15.1 percentage-point gap measures.

\texttt{Qwen2.5:3B} fails differently and more thoroughly. It spreads its
predictions across the label set roughly in proportion to nothing in
particular---CE 263, TLE 644, MLE 317, WA 715, RE 464, against a true WA share
of 76.6\%---so its balanced accuracy (0.348) is barely above chance for five
classes, and 10.1\% of its responses are unusable. We read this as a documented
failure mode of small local models on numeric thresholding, not as evidence
about the ordering of methods in general.

\textit{A note on the pilot.} An earlier 207-submission pilot of DeepSeek-V3
(75.85\%) used single-item prompting with no worked examples, a protocol
superseded by the batched three-shot evaluation reported here; the two are not
directly comparable. For completeness, the full 2,672-submission partition was
also run under that superseded single-item protocol (DeepSeek-V3 78.29\%,
\texttt{Qwen2.5:3B} 11.34\%), and the ordering of supervised models above both
LLMs is unchanged (78.29\% $<$ 91.77\%). The batched three-shot results are
reported throughout; the episode illustrates why protocol details must be
fixed before LLM comparisons are quoted.

\textit{What the worked examples do.} The two superseded single-item runs and
the three-shot evaluation share one test partition, which lets the examples'
effect be measured rather than asserted. Without examples, DeepSeek-V3 answers
Wrong Answer for 95.0\% of submissions (2,539 of 2,672; prediction entropy
0.35 bits), recovering only 17.9\% of compilation errors and 1.9\% of
time-limit verdicts---the platform encoding is present in the features but the
model never applies it. With three worked examples the same model applies the
encoding immediately: compilation-error recall rises to 1.00 and the
prediction distribution spreads to 62.6\% Wrong Answer (entropy 1.45 bits,
$4.2\times$ the no-example value), at the price of precision on the
equivalence cell (0.32) and 1.6\,pp of accuracy, because Wrong Answer is
usually the right answer and the examples buy coverage of the
execution-defined classes, not calibration of the prior inside the all-zero
cell. The examples thus select \emph{whether} the encoding is applied; they do
not supply the calibrated prior that the cell would require. The two runs
differ in call format as well as in example count (single-item versus eight
per call), so the comparison fixes the mechanism's direction and size on this
pair of runs rather than a controlled dose-response; a 15-example arm at fixed
batching is the natural confirmation and is left to future work.

figure quoted here from the archived prediction files.)

\subsection{Broader Implications for Computing Education Research}

Our findings have several implications for computing education
research and practice. First, the strong performance of metadata-only
classification (91.8\% accuracy without source code access) indicates that
\textit{submission logs alone} constitute a sufficiently rich signal for
error pattern recognition, opening new possibilities for privacy-preserving
educational analytics. Platforms that cannot access student source code
due to privacy policies (e.g., proctored exams, IRB constraints) can
still deploy effective verdict classification systems.

Second, the cost gap between traditional ML and frontier API models---four to
six orders of magnitude per prediction at list prices---has practical
significance for resource-constrained educational contexts. A semester-long
deployment for 500 students generating approximately 500,000 submissions would
cost approximately \$0.06 in Random Forest inference (about 11\,ms per thousand on a
single core) against roughly \$5 in DeepSeek-V3 API calls and \$47 at GPT-4o
list prices; local Ollama inference has near-zero marginal cost (no API
fees, only electricity) but requires upfront hardware investment, so the
trade-off is dominated by hardware availability rather than per-query fees.
All three figures are small next to instructor time, which is what makes the
latency and privacy differences, not price, the deciding factors. This cost
structure is particularly relevant for MOOCs and competitive programming
platforms serving millions of users.

\subsubsection{Empirical Generalization Analysis}\label{sec:skill-tier}
To assess generalizability beyond typical competitive programming
distributions, we segmented the shared test partition into three
problem-difficulty tiers---novice (rating $<$1,400), intermediate
(1,400--1,999) and advanced ($\geq$2,000)---and evaluated the Gradient
Boosting model of Table~\ref{tab:ml-results} on each tier.

Accuracy declines with problem difficulty: 93.60\% on intermediate problems
(n=734, macro F1=0.766), 92.21\% on novice problems (n=1,464, F1=0.794) and
87.55\% on advanced problems (n=474, F1=0.811), with balanced accuracy of
0.777, 0.826 and 0.803 respectively. The decline is compositional rather than
a failure of the classifier: advanced problems carry a more diverse verdict
mix---TLE 17.5\% and MLE 5.5\% of the tier, against 3.3\% and 0.2\% for novice
problems---and Runtime Error, the class the model handles worst overall
(F1 0.33), is more frequent there (10.3\% against 4.1\%). RE F1 is
non-monotonic across tiers (0.41 novice, 0.15 intermediate, 0.31 advanced);
the intermediate tier contains only 22 runtime errors, so we read the pattern
as composition and small-support noise rather than as difficulty-dependent
degradation. WA recall stays above 0.94 in every tier.

This subpopulation analysis extends prior work on fine-grained error
classification~\cite{altadmri2015most} by demonstrating that metadata-based ML
generalizes across difficulty levels, with accuracy maintained at 87.6\% even
for the hardest problems, where the verdict mix is most diverse.

\textbf{Population external validity:} The skill-tier analysis demonstrates
internal generalizability across competitive programming expertise levels, but
the gap to CS1/CS2 student populations~\cite{yadav2021collaborative}
remains open. Competitive programmers differ from novices in error cause and
submission behavior (iterative learning under low time pressure versus
competitive time pressure), and the two populations are measured differently:
the largest novice corpus records only compiler-detected mistakes~\cite{altadmri2015most},
so no published figure puts novice runtime-error rates beside ours.
Validation on student datasets (\emph{CS1QA}~\cite{lee2022cs1qa}, Blackbox)
is needed before drawing conclusions for novice education.



\textbf{Theoretical CS1 projection:}\label{sec:cs1-projection} We cannot compute a
submission-level weighted F1 for a CS1 population, because no published novice
dataset records the verdict distribution we would need: the largest such
corpus~\cite{altadmri2015most} contains only compiler-detected mistakes, and
runtime and wrong-answer failures produce no diagnostic and therefore never
enter it. What that corpus does show is the direction of the shift. Among the
mistakes it can see, compile-time categories dominate---the single most frequent
mistake alone (mismatched brackets) accounts for roughly a third of all
occurrences---whereas compilation errors are 7.3\% of our corpus. If a novice
population moved even a modest share of its mass from WA toward CE, the weighted
F1 would fall, because CE is the class the equivalence cell constrains most
tightly (F1 0.77 against a 0.767 identifiability ceiling) while WA sits at 0.95.
We therefore report the direction rather than a number, and we report it for the
same reason we report the equivalence ceiling: a transfer claim is only as good
as the assumption that per-class F1 is invariant across populations, and
Section~5.3 gives reason to doubt it. In a population where compilation errors
dominated, the all-zero cell would be composed differently, and CE F1 would move
with the composition rather than staying at 0.77. Direct validation on student
datasets (\emph{CS1QA}~\cite{lee2022cs1qa}, Blackbox) is required before any
claim about CS1 populations.



Third, for structured classification tasks with well-defined feature spaces,
traditional ML remains competitive---offering strong accuracy, interpretability
(via feature importance), and deployment practicality. A \textit{hybrid
strategy} (ML for classification, LLM for explanation) leverages both
paradigms.

Fourth, the gap between the 207-submission pilot (75.85\%) and the full
2,672-submission evaluation (76.65\% on valid outputs) for DeepSeek-V3 warns
against quoting LLM numbers from small pilots whose prompting protocol differs
from the final one; future work should report pilot and full-test results
under an identical protocol with explicit sample representativeness discussion.

\subsection{Limitations and Future Work}\label{sec:limitations}

While our study provides a systematic comparison of ML and LLM methods
for metadata-based verdict classification, several limitations should be
acknowledged.

We tested two LLM configurations (DeepSeek-V3 and \texttt{Qwen2.5:3B}) under an identical three-shot
protocol (Section~\ref{sec:llm-eval}); recent benchmarks~\cite{denny2024prompt}
confirm substantial LLM family variation, and alternative model families (GPT-4o, Claude-3.5 Sonnet) would increase inference cost substantially---at standard list prices (\$2.50/\$10.00 and \$3.00/\$15.00 per million input/output tokens) the same eight-item protocol runs about $9\times$ and $12\times$ DeepSeek-V3 per 1{,}000 predictions. The three-example dose is itself a limitation: the worked examples decide whether the platform encoding is applied at all (Section~\ref{sec:llm-analysis}), but the no-example arm differs from the reported arm in call format as well as example count, and a 15-example arm at fixed batching---the natural dose-response confirmation---was not run for lack of an API key at the time of writing.

\textbf{Student-population validation (critical gap):} Our dataset consists of competitive
programmers (rating 800--3,500), not novice students. CS1/CS2 error distributions differ substantially: in the largest novice corpus, 47.6\% of compilation events fail to compile~\cite{altadmri2015most}, against 7.3\% compilation-error verdicts in ours, and that corpus records compilation events only, so it offers no runtime-verdict figure to set beside our 4.9\% RE share. Before classroom deployment, three validations are needed: (1) CE/TLE/MLE accuracy on student submissions; (2) WA$\leftrightarrow$RE boundary behavior with novice error profiles; (3) whether automated classification translates to improved learning outcomes (randomized controlled trial). We provide a theoretical CS1 projection (Section~\ref{sec:cs1-projection}) and skill-tier analysis (Section~\ref{sec:skill-tier}) as partial evidence, but these do not substitute for direct student-population validation.

\textbf{Linear Baseline Underperformance:} Logistic Regression reaches 85.63\%
(Table~\ref{tab:ml-results}), above the majority-class rule (76.61\%) but 6.1\,pp
below the ensembles, and its Macro F1 collapses to 0.494 because it recovers 5
of 196 compilation errors. The deficiency is representational rather than
statistical: a linear boundary cannot express the conjunction of zero-valued
measurements that defines a compilation error. It is not repaired by tuning---the
model converges in 91 iterations and the gap persists under submitter-disjoint
evaluation (87.15\%). We retain LR as an interpretable floor; it should not be
deployed for verdict classification.



\textbf{Paired-Test Independence Assumption:} McNemar's test assumes independence
across the 2,672 paired test instances, but 503 of 801 test users (63\%) contribute
multiple submissions clustered around a characteristic verdict (mean modal-verdict
share 0.92; random baseline 0.20). We therefore report the McNemar $p$-values as a
\emph{lower bound} on uncertainty, not exact probabilities, and confirmed robustness
through a fully user-disjoint replication (Section~\ref{sec:robust}): Gradient
Boosting retained 93.13\% accuracy (92.15\% CV) and the ML $>$ LLM ranking held. A cluster-robust
McNemar variant is recommended for confirmatory replications seeking exact $p$-values.
The small RE ($n=131$) and MLE ($n=40$) test subsets further limit per-class F1 precision.

\textbf{Feature Set Limitations:} We used six metadata fields and did not
collect or evaluate source-code features (ASTs, token sequences, code embeddings).
The claim that source-code analysis is \emph{necessary} to resolve the
WA$\leftrightarrow$RE boundary is therefore a hypothesis, though a better
supported one than a bare failure would provide: the equivalence analysis of
Section~5.3 shows that the two verdicts share execution signatures, and that
more than half of the RE$\rightarrow$WA errors occur inside cells shared with
WA. What remains undemonstrated is that source features would suffice---we did
not test them. Source-code features~\cite{allamanis2018learning}
\emph{could} improve RE classification, but this remains to be verified in future work. More granular taxonomies (e.g., distinguishing segfault, division-by-zero, and assertion failure within RE) could enable more targeted feedback~\cite{altadmri2015most}, but this is orthogonal to the metadata-separability question examined here.

\textbf{Breadth Without Depth:} The dataset is broad in programmers (4,005) but
shallow per programmer (median two submissions). Any user-level quantity
therefore rests on few observations per person: a WA-rate aggregate rests on a
median of three earlier training submissions where any exist, adds no gain that
survives correction, and is exactly zero on the submitter-disjoint split
(Section~\ref{sec:ablation}). For the same reason the
skill-tier analysis pools programmers by rating band rather than estimating
individual trajectories.
Conclusions about individual learners should not be drawn from this dataset; a
course deployment that observes each student weekly would estimate these
quantities far more precisely.

\textbf{LLM Inference Cost:} We used local Ollama (\texttt{Qwen2.5:3B}) at no
API cost; future work should evaluate local LLM deployments for stable cost,
performance, and privacy in educational settings.

\textbf{Ethical and Fairness Considerations:} Deploying automated verdict
classifiers in educational settings introduces fairness risks that warrant
explicit scrutiny. First, misclassified error types produce mis-targeted
pedagogical feedback: a RE incorrectly labeled WA (or vice versa) can lead a
learner to debug the wrong component or, worse, to believe a failing solution
is correct. Second, this harm is not evenly distributed. Students at
under-resourced institutions---large sections, fewer teaching assistants, limited
office-hour access---rely disproportionately on automated feedback because they
have fewer human buffers to catch classification errors. A false positive that a
well-resourced peer would immediately overturn in a staffed lab may persist
uncorrected for a under-resourced student across an entire assignment cycle.
Third, the platform-encoding boundary (Section~3.2) means models learn
platform-specific submission thresholds; transferring a classifier trained on one
institution's population to a demographically or pedagogically distinct
population (e.g., a school with a different error mix, more syntax errors, less
competitive exposure) risks systematic, population-specific misclassification
rather than random error. Fourth, the accuracy--Macro~F1 tension documented in
our LLM analysis (Section~\ref{sec:llm-eval}) generalizes: aggregate accuracy rewards the
dominant WA class and can mask under-served minority errors (RE, MLE)---precisely
the harder failures where under-resourced students most need accurate diagnosis.
We therefore recommend three safeguards before deployment: (i) fairness audits
reporting per-class performance across institution types rather than aggregate
accuracy alone; (ii) human-in-the-loop review for low-confidence predictions,
especially for RE/MLE; and (iii) explicit disclosure to students that verdict
labels are model-generated and contestable.

Despite these limitations, our findings provide strong evidence that
traditional ML methods remain highly competitive for metadata-based error
classification, offering a cost-effective alternative to LLM-based approaches.

\section{Threats to Validity}\label{sec:threats}

\textbf{Internal Validity:} Stratified 5-fold CV and McNemar's test mitigate
split-dependent biases. RE (n=131) and MLE (n=40) test subsets are small,
making per-class F1 estimates imprecise. CE/TLE/MLE predictions partially reflect
platform threshold encoding; ablation (Table~\ref{tab:ablation}) shows 7.3pp
drop but non-zero residual accuracy, confirming complementary signals.

\textbf{External Validity:} Our data comes from competitive programmers
(median Codeforces rating below 1,400), and student error patterns differ
(more CE, fewer complex RE). We evaluate cross-population generalizability via a
skill-tier analysis (Section~\ref{sec:skill-tier}); the full gap analysis and
validation agenda appear in Section~\ref{sec:limitations}.

\textbf{Construct Validity:} The Codeforces error taxonomy (designed for
competition judging) does not align with educational error taxonomies. RE is
heterogeneous (segfault, division by zero, etc.), and WA encompasses diverse
root causes. A more nuanced taxonomy would provide greater educational
utility.

\subsection*{LLM Prompt Template (Three-Shot)}
\label{sec:prompt-template}
Both LLM configurations received the same three-shot prompt. Each request
classified eight submissions at a time and carried three worked examples (one
each for CE, TLE and MLE), so the protocol is three-shot rather than
zero-shot; no fine-tuning was performed. The five metadata fields
(\texttt{problem\_rating}, \texttt{language}, \texttt{time\_consumed\_ms},
\texttt{memory\_kb}, \texttt{passed\_test\_count}) were serialized one
submission per line, with \texttt{language} normalized to a family (e.g.,
``C++23 (GCC 14-64, msys2)'' $\rightarrow$ ``C++''). Temperature was 0 for
both models. DeepSeek-V3 additionally received the system message
``\textit{You are a competitive-programming error classifier. Respond with only
a valid JSON object.}'' and used grammar-constrained JSON output;
\texttt{Qwen2.5:3B} used Ollama's JSON format constraint. The model returned a
JSON object with key \texttt{verdicts} holding one label per item from the set
\{WA, TLE, RE, CE, MLE\}; items whose position could not be parsed were counted
as invalid outputs (DeepSeek-V3 21/2{,}672; \texttt{Qwen2.5:3B} 269/2{,}672).
An earlier single-item zero-shot variant was superseded by this protocol
(Section~\ref{sec:llm-analysis}). The two instruction lines below are wrapped
for display; the prompt sent to the models joined each into a single line.

\begin{verbatim}
Classify each competitive-programming submission error into exactly one of:
WA, TLE, RE, CE, MLE.
Example rating=1400 lang=C++ time_ms=0 mem_kb=0 passed=0 -> CE
Example rating=1800 lang=C++ time_ms=1987 mem_kb=1024 passed=0 -> TLE
Example rating=2000 lang=C++ time_ms=500 mem_kb=262144 passed=0 -> MLE
Classify each item. Return a JSON object with key 'verdicts' =
array of one token per item, in the same order.
[0] rating=1400 lang=C++ time_ms=15 mem_kb=0 passed=0
[1] rating=1000 lang=Kotlin time_ms=156 mem_kb=0 passed=0
[2] rating=1300 lang=C++ time_ms=15 mem_kb=100 passed=0
[3] rating=1300 lang=C++ time_ms=2000 mem_kb=6300 passed=1
[4] rating=1800 lang=C++ time_ms=0 mem_kb=0 passed=0
[5] rating=2200 lang=Java time_ms=0 mem_kb=0 passed=0
[6] rating=800 lang=C++ time_ms=62 mem_kb=0 passed=1
[7] rating=1200 lang=C++ time_ms=31 mem_kb=0 passed=1
Verdicts:
\end{verbatim}

\section{Conclusion}

This study asks how much verdict information a submission log carries. The
answer is not a single accuracy figure but a decomposition. Of the 13,360
submissions, 18.5\% are decided by measurements the platform already
publishes: Time Limit Exceeded (F1 0.99) and Memory Limit Exceeded (0.95) are
recoverable because the judge's own thresholds define them, while Compilation
Error (0.77) is recoverable only up to the point where its zero-millisecond
signature coincides with an early crash or a first-test wrong answer. That
coincidence---11.3\% of the corpus lying in one signature cell that spans three
verdicts---is what limits metadata-only classification, and the
Wrong Answer$\leftrightarrow$Runtime Error boundary is the same phenomenon with
a different pair of verdicts. A gradient-boosted model over six metadata fields
reaches 91.77\% (balanced accuracy 0.80), leads the strongest prompted LLM by
15.1\,pp at four to five orders of magnitude lower per-prediction inference
cost, and is unchanged under
submitter-disjoint evaluation (93.13\%), which shows that the estimate does not
depend on seeing the same person twice. Execution time is the dominant
predictor (7.3\,pp drop, 81.5\% of Gini importance), and a submitter-history
aggregate---the standard first feature in this literature---adds nothing
reliable: a nominal 0.67\,pp that does not survive correction, and exactly zero
when submitters are disjoint.

\paragraph{Future directions.}\label{sec:future} Three next steps follow from the
equivalence account rather than from the model comparison. First,
\textbf{audit the cells elsewhere}: computing the same signature analysis on
LeetCode or AtCoder logs would show whether the all-zero and first-test-failure
cells are a general property of judge architectures or an artefact of how
Codeforces reports. Second, \textbf{collect the two missing measurements}: the
compiler diagnostic and the index of the first failing test are held by every
major judge but not published. Recovering them for a sample would let one
measure directly how much of each equivalence class splits---a sharper
experiment than adding source code wholesale, and one that yields a cost curve
for platform designers. Third, \textbf{classroom validation}: the same pipeline
run on a course deployment, where per-student histories are long enough for
user-level features to be estimated rather than guessed.

Practically, the boundary tells platform developers where to draw the line
between automated and code-level feedback. The execution-encoded verdicts are
exactly those for which immediate, specific feedback is both cheap and
actionable: a compilation error warrants syntax guidance, a time-limit verdict
warrants complexity analysis. At the Wrong Answer$\leftrightarrow$Runtime Error
boundary the system should abstain rather than guess, report the ambiguity, and
route the submission to a diagnostic that reads the code; calibrated abstention
is itself pedagogically useful, because it tells the learner which question to
ask. A hybrid deployment---ML for fast, cheap classification, LLMs invoked only
at the boundary for explanation---follows from this division of labour, though
we emphasise that the hybrid configuration was not evaluated here.
